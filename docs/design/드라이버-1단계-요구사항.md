## 1. 페르소나 및 목적

**누가 (Who)**
신선 화훼·농산물을 소비자에게 직접 배송하는 드라이버.
MVP: 꽃차를 직접 운행하는 디어 오키드 운영자(판매자 겸 드라이버). 이후 외부 전문 드라이버로 확장.

**무엇을 (What)**
오늘의 배송 목록 확인, 카카오맵 기반 경로 안내, 배송 단계별 상태 변경, 거점 하차 사진 인증을 하나의 모바일 앱에서 수행.

**왜 (Why)**
판매자·소비자 앱과 실시간으로 연동된 FSM 기반 상태 변경을 현장에서 즉시 처리하고,
배송 완료 인증 사진을 남겨 분쟁을 예방하며, 향후 운행 데이터 축적을 통해 배송 표준을 수립하기 위함.

## 2. 사용자 스토리

| # | 스토리 | 연결 기능 |
|---|--------|----------|
| D1 | 나는 카카오 로그인 한 번으로 드라이버 앱에 접속하고 싶다. 판매자 계정이 있다면 별도 가입 없이 그대로 사용하고 싶다. | 인증 |
| D2 | 나는 오늘 수거해야 할 주문 목록을 한눈에 보고, 준비 완료 예정 시간이 표시된 순서로 확인하고 싶다. | 배송 작업 보드 |
| D3 | 나는 여러 배송지를 들러야 할 때 시스템이 제안하는 최적 순서를 지도에서 확인하고 싶다. | 경로 시각화 |
| D4 | 나는 주행 시작 버튼 한 번으로 카카오내비가 자동 실행되어 안내를 받고 싶다. | 내비게이션 딥링크 |
| D5 | 나는 수거 완료, 배송 출발, 거점 도착, 배송 완료 각 단계에서 버튼을 눌러 소비자가 실시간 알림을 받게 하고 싶다. | 상태 트리거 |
| D6 | 나는 거점에 도착했을 때 하차 사진을 찍어 증빙으로 남기고 싶다. | 하차 인증 사진 |
| D7 | 나는 배송 중 판매자 또는 소비자와 즉시 연락이 필요할 때 앱에서 바로 전화를 걸고 싶다. | 연락처 바로가기 |

## 3. 핵심 기능 목록

### ✅ Must Have (필수 구현)

---

#### 인증

- 로그인: **카카오 OAuth** (NextAuth.js — seller 앱과 동일한 Provider 구성)
- **허용 role**: `seller` 또는 `driver` 둘 다 입장 허용 (middleware에서 체크)
  - MVP: 판매자(role: `seller`)가 자신의 카카오 계정으로 드라이버 앱에 로그인
  - 외부 드라이버: 본인 카카오 계정으로 가입 → Admin이 Firestore에서 `role = 'driver'` 수동 설정
- **이메일 로그인 미지원**: 드라이버 앱은 카카오 OAuth 단일 경로만 제공

> **설계 의도**: 하나의 카카오 계정은 단일 role을 가진다. 드라이버 앱 middleware가 `seller | driver` 두 role을 모두 허용함으로써 판매자 겸 드라이버 케이스를 별도 계정 없이 처리한다. 계정 자체가 두 권한을 동시에 갖는 것이 아님. (`docs/specs/auth.md` §4 참조)

---

#### 배송 작업 보드 (Task Board)

- 수거 대기 주문 목록: `status = PREPARING` 주문을 `preparedAt` 오름차순 정렬 (수거 예정 시간 빠른 순)
- 주문 카드 표시 항목:
  - 배송 유형: 직배송(`direct`) / 거점 픽업(`hub`) 뱃지
  - 소비자 이름 · 배송지 주소 (거점 픽업 시 거점명 + 주소)
  - 판매자가 설정한 수거 예정 시간 (`preparedAt`)
  - 상품명 · 수량
- 진행 중 배송 탭: `status = DELIVERING` 주문 별도 노출
- Firestore 실시간 리스너 기반 목록 갱신

> **API 현황**: `GET /stores/:storeId/orders?status=PREPARING` 구현 완료. `driverId` 필터는 추가 필요.

---

#### 카카오맵 기반 경로 시각화

- 수거 대기 주문의 배송지 주소를 **카카오맵 Web SDK**로 지도에 마커 표시
- 경유지 목록을 거리 기반으로 정렬하여 추천 방문 순서 표시 (Nearest Neighbor 알고리즘)
- **카카오내비 딥링크**: 주행 시작 버튼 클릭 → `kakaomap://route?ep=...` 호출로 카카오내비 앱 자동 실행

> **지도 인프라 전략**: `KakaoMapAdapter` 인터페이스로 감싸 구현. Phase 2에서 TmapAdapter로 교체 시 드라이버 앱 코드 변경 없음. (`docs/배송 관련 추가 검토사항.md` §지도 로드맵 참조)

---

#### 실시간 상태 트리거

드라이버가 수행하는 상태 전환 (`PATCH /stores/:storeId/orders/:orderId/status`):

| 버튼 | 전환 | 트리거 조건 |
|------|------|-----------|
| 수거 완료 / 배송 시작 | `PREPARING → DELIVERING` | 판매자 창고에서 상품 픽업 후 |
| 거점 도착 완료 | `DELIVERING → HUB_ARRIVED` | 거점(hub) 배송 주문에서만 노출 |
| 배송 완료 | `DELIVERING → DELIVERED` | 직배송 주문에서만 노출 |

- 상태 전환 시 소비자 앱 실시간 상태 바 즉시 갱신 (Firestore 리스너)
- 상태 전환 시 카카오 알림톡 자동 발송 (기존 알림 시스템과 동일 채널)

> **현재 임시 처리**: `PREPARING → DELIVERING` 전환은 현재 seller 앱에서도 가능하도록 구현되어 있음 (드라이버 앱 완성 전 임시 조치, `orders.helpers.ts` 주석 참조). 드라이버 앱 배포 후 seller 앱에서의 DELIVERING 전환 제거 여부는 운영 방식에 따라 결정.

---

#### 거점 하차 인증 사진

- 거점(`hub`) 배송 주문에서 `HUB_ARRIVED` 전환 시 사진 촬영 화면 진입
- Firebase Storage 업로드 → `deliveryPhotos/{orderId}_{timestamp}.jpg`
- 업로드 완료 후 `orders.deliveryPhotoUrl` 저장 + `HUB_ARRIVED` 상태 전환
- **노출 범위**:
  - Seller 앱 주문 상세: 배송 완료 증빙으로 표시
  - Consumer 앱 주문 상세: "거점 도착 사진" 섹션 (선택적 노출 — IA에서 결정)
- **비용**: 사진 1장 압축 기준 ~500KB, 1,000건/월 기준 월 $0.02 수준으로 무시 가능

> **API 현황**: `orders.deliveryPhotoUrl` 필드 신규 추가 필요. `PATCH /stores/:storeId/orders/:orderId/status` 요청 body에 `photoUrl` 파라미터 추가 필요.

---

#### 연락처 바로가기

- 배송 상세 화면에서 소비자 연락처 표시 + `tel:` 딥링크로 즉시 전화 연결
- **드라이버 정보 → 판매자 노출**: 드라이버가 `DELIVERING` 전환 시 `orders.driverId` 저장 → Seller 앱 주문 상세에서 드라이버 이름 · 전화번호 표시 (판매자가 드라이버에게 전화 가능)
- **소비자에게는 드라이버 개인정보 미노출**: 소비자 앱에는 드라이버 상태 메시지만 표시

> **실시간 GPS 미구현 결정**: 실시간 위치 추적은 구현 복잡도 대비 MVP 효용이 낮음. 드라이버 연락처 노출로 대체. Phase 2에서 지도 기반 실시간 추적 검토.

---

## 4. 비기능 요구사항

### 현장 편의성 (최우선)
- **큰 버튼, 고대비 UI**: 야외 햇빛 아래에서도 가독성 확보. 핵심 액션 버튼은 최소 56px 높이
- **단계별 가이드**: 현재 해야 할 액션 하나만 화면에 강조 (멀티 태스킹 배제)
- 한 손 조작을 고려한 하단 집중 레이아웃

### 성능
- 모바일 네트워크(LTE/5G)에서 화면 전환 1초 이내
- Firestore `memoryLocalCache()` 적용 (seller 앱과 동일 — 오프라인 캐싱 미지원)
  - 드라이버가 각 배송지에서 앱을 열어 확인하는 패턴이므로, 매 조작 시 온라인 상태가 보장됨

### 실시간성
- Firestore 실시간 리스너: 판매자가 새 주문을 PREPARING으로 전환하면 드라이버 보드에 즉시 노출

### 보안
- `storeId` 소유권 검증: 드라이버는 자신이 배정된 `storeId` 주문만 접근 가능
- 배송 사진 Storage 직접 접근 차단: URL 공개, 직접 업로드 경로 차단 (Firebase Storage Rules)

## 5. 기술 스택 결정

| 항목 | 선택 | 비고 |
|------|------|------|
| 프레임워크 | Next.js (App Router) | seller 앱과 동일, `apps/driver` |

| 실시간 | Firestore 실시간 리스너 | 배송 목록 실시간 갱신 |

| 사진 업로드 | Firebase Storage SDK (클라이언트) | URL만 Firestore에 저장 |
| 스타일 | Tailwind CSS | 다크 모드 `dark:` 클래스 포함 |

> **신규 API 개발 필요 항목**: `orders.driverId` 필드 저장 로직, `orders.deliveryPhotoUrl` 필드 + PATCH 파라미터 추가

## 6. MVP 범위 및 외부 드라이버 확장 계획

### MVP (현재)
```
- 단일 드라이버: 디어 오키드 운영자 (role: 'seller')
- 드라이버 앱 middleware: role 'seller' | 'driver' 둘 다 허용
- role 변경: Admin이 Firestore Console에서 수동 설정 (건수 적음)
- GPS 실시간 추적 없음 → 드라이버 연락처 노출로 대체
```

### Phase 2 (외부 드라이버 고용)
```
추가 개발 항목:
  - /admin/users 화면에 role 변경 드롭다운 추가 (현재 Firestore Console 수동)
  - 드라이버별 배송 건수 · 완료율 통계 (admin 화면)
  - 드라이버 배차 UI: seller 앱에서 주문별 드라이버 지정
  - 지도 기반 실시간 위치 추적 (판매자/관제 전용)
  - Tmap Mobility API 교체 (KakaoMapAdapter → TmapAdapter)

변경 불필요 항목:
  - FSM 상태 전환 로직 (driverId 필드만 활용 방식 확장)
  - 알림 시스템
  - Firebase Storage 인증 사진 구조
```

## 7. DB 스키마 추가 정의

> 기존 스키마(소비자·판매자 설계 1단계)에 드라이버 앱 구현을 위해 추가되는 항목만 기술.

### orders (필드 추가)

```ts
orders {
  // 기존 필드 유지 (소비자·판매자 설계 1단계 스키마 참조)
  // ...

  // 드라이버 앱에서 신규 추가
  driverId: string | null          // 배송 시작(DELIVERING) 시 드라이버 userId 기록
                                   // → Seller 앱 주문 상세에서 드라이버 이름·연락처 조회 용도
  deliveryPhotoUrl: string | null  // 거점 하차 인증 사진 (Firebase Storage URL)
                                   // HUB_ARRIVED 전환 시 업로드 후 저장
                                   // 직배송·택배는 null
}
```

### FSM 전환 권한 (드라이버 추가분)

```
현재 구현된 전환 권한 (orders.helpers.ts getAllowedTransitions):

  seller: ACCEPTED·CONFIRMED → PREPARING
          PREPARING → DELIVERING  ← 드라이버 앱 완성 전 임시 허용
          ACCEPTED·CONFIRMED·PREPARING → CANCELLED

  driver: PREPARING → DELIVERING   ← 드라이버 앱 배포 후 주 경로
          DELIVERING → DELIVERED
          DELIVERING → HUB_ARRIVED

  consumer: DELIVERING·HUB_ARRIVED → CANCELLED (제한됨)
            DELIVERED·PICKED_UP → REVIEWED
```
