# 어드민 정산 일괄 지급 SDD

> **작성일**: 2026-05-29  
> **상태**: 설계 확정, 구현 대기  
> **출처**: `admin-tab-settlements-plan.md` D-6-1, F2 일괄 지급 게이트  
> **범위**: `/admin/settlements` 화면의 confirmed 정산 다중 선택과 백엔드 일괄 지급 API

---

## 1. 목표

어드민이 정산 마감 후 `confirmed` 상태의 정산 여러 건을 선택해 한 번에 `paid`로 전환한다.

**단건 지급의 기존 트랜잭션 안전성은 유지하고, 일괄 지급은 부분 성공을 허용한다.** 한 건이 실패해도 다른 정상 건의 지급 처리는 계속 진행하며, 프론트는 성공·실패를 분리해 운영자가 후속 조치를 알 수 있게 한다.

---

## 2. 비범위

- 정산 자동 마감 또는 자동 지급 스케줄링
- 스토어명 조인, 은행 계좌 검증, 지급 대행사 연동
- 500건 초과 페이지네이션 또는 커서 기반 일괄 처리
- `pending`, `paid`, `cancelled` 상태의 강제 전이

---

## 3. API 계약

### 3-1. 일괄 지급

```
POST /admin/settlements/bulk-pay
```

**Request Body**

```ts
{
  ids: string[] // 1~500개 정산 ID
}
```

**Response 200**

```ts
{
  ok: string[]
  failed: Array<{
    id: string
    reason: string
  }>
}
```

**검증 규칙**

| 항목 | 규칙 |
|------|------|
| 권한 | 기존 admin API와 동일하게 `@Roles('admin')` 필수 |
| 배열 크기 | 최소 1개, 최대 500개 |
| ID 타입 | 모든 항목은 문자열 |
| 중복 ID | 서버 진입 시 `Set`으로 중복 제거 |
| 상태 전이 | `confirmed`만 `paid` 전환 가능 |
| 응답 의미 | `ok`는 지급 완료 ID, `failed`는 실패 ID와 사용자 표시 가능한 사유 |

---

## 4. 트랜잭션 전략

일괄 지급은 **단건 `markAsPaid`와 같은 조건부 트랜잭션을 ID별로 반복**한다.

**선택 이유**

- 단건 지급의 동시성 방어를 재사용한다.
- 일부 정산이 이미 `paid`이거나 `confirmed`가 아니어도 나머지 정산을 지급할 수 있다.
- batch write는 모든 문서 상태를 사전에 읽어야 하고, 부분 실패 사유를 명확히 표현하기 어렵다.
- 500건 상한은 Firestore 비용과 UI 조작 범위를 동시에 제한한다.

**실패 분류**

| 조건 | 실패 사유 |
|------|-----------|
| 문서 없음 | `정산 내역을 찾을 수 없습니다.` |
| 이미 `paid` | `이미 지급 완료된 정산입니다.` |
| `confirmed` 아님 | `confirmed 상태의 정산만 지급 처리할 수 있습니다.` |
| 기타 예외 | 예외 메시지가 있으면 사용, 없으면 `지급 처리에 실패했습니다.` |

## 5. 프론트 계약

### 5-1. 선택 가능 항목

- `SettlementTable`은 `confirmed` 상태 정산만 체크박스를 활성화한다.
- `pending`, `paid`, `cancelled` 행·카드는 체크박스를 비활성화하거나 선택 대상에서 제외한다.
- 전체 선택은 현재 필터·목록에서 선택 가능한 `confirmed` 항목만 대상으로 한다.

### 5-2. 액션 바

선택된 항목이 1개 이상이면 목록 위에 액션 바를 표시한다.

| 표시 항목 | 내용 |
|----------|------|
| 선택 건수 | 선택된 정산 수 |
| 지급 합계 | 선택된 정산의 `netAmount` 합계 |
| 일괄 지급 버튼 | 확인 모달을 연다 |
| 선택 해제 | 선택 상태를 모두 초기화 |

### 5-3. 확인 모달

모달은 선택 건수와 지급 합계를 다시 보여준다.

**확인 버튼 클릭 시**

1. `POST /admin/settlements/bulk-pay` 호출
2. `ok.length > 0`이면 목록 재조회
3. `failed.length === 0`이면 성공 알림
4. `failed.length > 0`이면 부분 실패 알림과 실패 건수 표시
5. 실패 상세는 알림 또는 접을 수 있는 영역으로 표시한다.

구현 후 `pending-visual-verify.md` §6의 항목을 모두 확인한다.

자동 e2e는 운영 DB 쓰기를 피하기 위해 route fixture 또는 별도 테스트 DB를 사용한다.

| 시나리오 | 기대 |
|----------|------|
| confirmed 다중 선택 | 액션 바의 건수·합계가 선택 상태와 일치 |
| 전체 선택 | confirmed만 선택되고 비대상 상태는 제외 |
| 전부 성공 | 요청 후 선택 건이 `paid`로 반영되고 목록 재조회 |
| 부분 실패 | 성공 건만 반영되고 실패 사유가 표시 |
| 모바일 카드 | 체크박스·액션 바·모달이 375px 폭에서 겹치지 않음 |
