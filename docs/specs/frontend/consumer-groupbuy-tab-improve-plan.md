# 소비자 공구 탭 안정화와 핵심 개선 선 설계

> 기준일: 2026-06-17
> 범위: 소비자 앱 `/groupbuy`, 공구 상품 카드, 상품 상세 공구 구매 영역, 관련 E2E
> 관련 문서: `docs/specs/frontend/consumer-home-groupbuy-improve-plan.md`, `docs/specs/frontend/consumer-category-exploration-plan.md`, `docs/specs/frontend/delivery-date-selection-plan.md`, `docs/specs/api/products.md`, `docs/specs/api/orders.md`

## 1. 목적

소비자 공구 탭을 단순 상품 목록에서 공구 참여 여부를 빠르게 판단할 수 있는 화면으로 개선한다. 1차 범위는 안정화와 핵심 개선을 함께 처리한다. 사용자는 공구 상태, 마감, 달성률, 배송일, 참여 가능 여부를 같은 기준으로 확인해야 하며, 상세 구매 흐름은 판매자가 지정한 공구 조건과 어긋나지 않아야 한다.

## 2. 주요 발견 문제

| ID | 문제 | 영향 | 근거 |
| --- | --- | --- | --- |
| P1 | 공구 상태 판단이 `currentQuantity >= targetQuantity` 중심이다. | 마감됨, 최소수량 미달, 처리 완료 같은 상태가 진행 중으로 보일 수 있다. | `/groupbuy`, `ProductCard`, `DeadlineSection` |
| P2 | 공구 설정이 없는 상품을 진행 중으로 분류한다. | `groupSummary` 누락 상품이 실제 참여 가능한 공구처럼 보일 수 있다. | `/groupbuy`의 active 분기 |
| P3 | 공구 목록 API가 공구 설정 병합을 30개까지만 처리한다. | 31번째 이후 공구 상품은 진행률과 마감 정보가 누락될 수 있다. | `products.service.ts`의 `in` 쿼리 |
| P4 | 상세 구매 영역에서 공구 배송 방식 선택지가 일반 상품처럼 노출된다. | 소비자가 판매자 지정 배송 방식과 다른 값으로 주문할 수 있다. | `ProductActions` |
| P5 | 공구 진행률 기준이 목록과 상세에서 다르다. | 목록은 목표수량 기준, 상세는 최소수량 기준으로 보일 수 있다. | `ProductCard`, `ProductActions` |
| P6 | 공구 동의 문구와 안내 문구가 일부 화면에서 깨졌거나 이해하기 어렵다. | 참여 조건과 취소 제한을 소비자가 오해할 수 있다. | 공구 탭, 상품 카드, 상세 동의 영역 |
| P7 | 공구 탭 E2E가 화면 계약보다 존재 여부 중심이다. | 상태 오분류, 문구 깨짐, 배송 방식 회귀를 놓칠 수 있다. | `consumer-groupbuy.spec.ts` |

## 3. 개선 방향

- 공구 상태 계산은 프론트 표시용 단일 도메인 유틸로 통일한다.
- 공구 설정이 없는 상품은 "정보 확인 필요" 상태로 분리하고 참여 CTA를 막는다.
- 공구 탭 카드는 상태, 달성률, 남은 수량, 마감일, 배송일을 우선 표시한다.
- 상세 구매 영역은 공구 상품에서 배송 방식 선택을 숨기고 `groupProductConfig.groupDeliveryMethod`를 사용한다.
- 공구 진행률은 목적을 분리한다. "최소 성립률"과 "목표 달성률"을 혼용하지 않는다.
- E2E는 사용자에게 보이는 한국어 문구와 주문 파라미터 정합성을 검증한다.

## 4. 정합성 기준

### 4.1 데이터 계약

| 항목 | 기준 |
| --- | --- |
| 판매 유형 | `SaleType`은 `normal | group`만 사용한다. `direct`는 배송 방식으로만 사용한다. |
| 공구 설정 | `saleType=group` 상품은 `groupProductConfig/{productId}` 또는 목록 응답의 `groupSummary`가 있어야 한다. |
| 마감일 | `recruitDeadline`은 ISO 문자열로 정규화해 비교한다. Firestore Timestamp를 직접 화면 계산에 쓰지 않는다. |
| 배송일 | 공구 배송일은 `groupDeliveryDate`를 따른다. 소비자 주문 단위 배송일을 받지 않는다. |
| 배송 방식 | 공구 배송 방식은 `groupDeliveryMethod`를 따른다. 소비자 선택 UI를 제공하지 않는다. |
| 진행 수량 | `currentQuantity`, `minQuantity`, `targetQuantity`는 0 이상 정수로 취급한다. `targetQuantity`가 0 이하이면 오류 상태로 본다. |

### 4.2 상태 계산

| 상태 | 조건 | 화면 의미 |
| --- | --- | --- |
| `missing_config` | 공구 상품인데 공구 설정이 없다. | 정보 확인 필요, 참여 불가 |
| `recruiting` | 마감 전이고 목표수량 미달이다. | 모집 중 |
| `target_reached` | 마감 전이고 목표수량 이상이다. | 모집 완료, 참여 불가 |
| `deadline_closed` | 마감 후이고 최소수량 이상이다. | 모집 종료, 확정 대기 또는 확정 |
| `failed_minimum` | 마감 후이고 최소수량 미달이다. | 모집 실패, 참여 불가 |
| `invalid_config` | 수량이나 날짜가 파싱 불가하다. | 정보 확인 필요, 참여 불가 |

### 4.3 화면 계약

- 공구 탭 상단은 진행 중 공구 개수와 마감 임박 개수를 구분한다.
- 모집 중 섹션은 참여 가능한 상품만 표시한다.
- 모집 완료 또는 마감 상품은 별도 섹션으로 분리한다.
- 정보 확인 필요 상품은 운영 확인 대상이며 일반 모집 중 목록에 섞지 않는다.
- 공구 상세에서는 배송 방식 버튼을 표시하지 않고, 지정 배송 방식과 배송일을 읽기 전용으로 보여준다.
- 장바구니 담기와 바로 결제는 공구 설정이 있고 모집 중이며 동의가 완료된 경우에만 활성화한다.

## 5. 아토믹 태스크

| ID | 작업 | 완료 기준 | 정합성 검토 |
| --- | --- | --- | --- |
| T1 | 공구 상태 계산 유틸 추가 | `getGroupBuyStatus()`가 상태와 표시 보조값을 반환한다. | `minQuantity`, `targetQuantity`, `recruitDeadline` 누락과 0 값을 모두 처리한다. |
| T2 | 상태 유틸 단위 테스트 추가 | 주요 상태 케이스가 테스트로 고정된다. | 마감 전후, 최소수량 미달, 목표 달성, 설정 누락을 포함한다. |
| T3 | 공구 탭 분류 로직 교체 | `/groupbuy`의 모집 중, 완료, 확인 필요 섹션이 상태 유틸을 사용한다. | `groupSummary` 누락 상품이 모집 중에 들어가지 않는다. |
| T4 | 공구 탭 카드 정보 보강 | 카드에 달성률, 남은 수량, 마감일 또는 상태 라벨이 보인다. | 목록과 홈 미리보기의 공구 표시 용어가 충돌하지 않는다. |
| T5 | 공구 상세 배송 방식 고정 | 공구 상품에서 배송 방식 선택 버튼이 사라지고 지정 방식이 표시된다. | 주문 URL과 장바구니 item의 `deliveryMethod`가 `groupDeliveryMethod`와 일치한다. |
| T6 | 공구 동의 문구 정리 | 취소 제한과 확정 조건이 깨지지 않은 한국어로 표시된다. | 동의 전 CTA 비활성, 동의 후 모집 중 CTA 활성 조건을 유지한다. |
| T7 | 목록 API 공구 설정 병합 보강 | 공구 상품 30개 초과 시에도 `groupSummary` 누락이 발생하지 않는다. | Firestore `in` 쿼리는 30개 단위로 나누어 조회한다. |
| T8 | E2E 계약 보강 | 공구 탭과 상세에서 상태, 문구, 배송 방식 고정이 검증된다. | 깨진 문자열 기준을 제거하고 사용자 노출 문구 기준으로 검증한다. |
| T9 | 회귀 검증 | 타입 검사, 린트, 소비자 빌드, 관련 E2E가 통과한다. | 기존 홈 공구 미리보기와 카테고리 공구 탭 동작을 함께 확인한다. |

## 6. 구현 순서

1. T1, T2로 상태 기준을 먼저 고정한다.
2. T3, T4로 공구 탭 표시를 교체한다.
3. T5, T6로 상세 구매 흐름의 주문 정합성을 맞춘다.
4. T7로 API 목록 계약의 누락 가능성을 제거한다.
5. T8, T9로 사용자 흐름과 회귀를 확인한다.

## 8. 검증 계획

| 검증 | 명령 또는 방법 | 기대 결과 |
| --- | --- | --- |
| 타입 검사 | `pnpm --filter consumer exec tsc --noEmit` | 통과 |
| 소비자 린트 | `pnpm --filter consumer lint` | 신규 오류 없음 |
| API 테스트 | 상품 목록 서비스 단위 테스트 또는 추가 테스트 | 30개 초과 공구 설정 병합 통과 |
| 공구 E2E | `pnpm --filter e2e test -- consumer-groupbuy.spec.ts` | 모집 중, 완료, 정보 확인 필요, 상세 이동 통과 |
| 상세 구매 E2E | 관련 상품 상세 또는 체크아웃 테스트 | 공구 배송 방식이 지정값으로 유지 |
| 시각 확인 | 데스크톱과 모바일에서 `/groupbuy`, `/products/:id` 확인 | 텍스트 깨짐, 겹침, CTA 오분류 없음 |

## 9. 출시 전 정합성 체크리스트

- [x] 공구 상태 유틸이 모든 공구 표시 화면에서 같은 기준으로 사용된다.
- [x] `saleType=group`과 `deliveryMethod=direct`가 혼동되지 않는다.
- [x] 공구 설정 누락 상품은 참여 가능한 목록에 섞이지 않는다.
- [x] 모집 완료 상품은 구매 CTA가 비활성화된다.
- [x] 마감 후 최소수량 미달 상품은 실패 상태로 보인다.
- [x] 공구 상세의 배송 방식은 판매자 지정값과 일치한다.
- [x] 공구 배송일은 소비자가 선택하지 않는다.
- [x] E2E는 깨진 문자열이 아닌 실제 한국어 문구를 기준으로 한다.

## 10. 잔여 질문

- 마감 후 최소수량 이상이지만 아직 알림 처리 전인 상품을 소비자에게 "모집 종료"로 보일지, "확정 대기"로 보일지 결정이 필요하다.
- 정보 확인 필요 상품을 소비자 화면에서 숨길지, 별도 안내로 노출할지 결정이 필요하다.
- API 보강을 이번 작업에 반드시 포함할지, 프론트 방어 로직 이후 별도 작업으로 분리할지 결정이 필요하다.
