# 소비자 장바구니 결제 전 방지 개선 계획

> 작업 ID: `CONSUMER-CART-PRECHECKOUT-GUARD`
> 기준일: 2026-06-17
> 원칙: **선(先) 설계 후(後) 구현**. 장바구니는 결제 직전 확인 화면이므로, 결제 가능한 상태와 불가능한 상태를 화면에서 먼저 분리한다.

---

## 목적

소비자 앱 장바구니 탭에서 문제 있는 상품을 결제 화면까지 보낸 뒤 차단하는 흐름을 줄인다. 장바구니를 열었을 때 결제 가능한 상품과 결제할 수 없는 상품이 즉시 구분되고, 문제가 남아 있으면 결제 버튼을 막는다.

## 배경

소비자 장바구니는 현재 `localStorage.greenhub_cart`에 저장된 항목을 렌더링하고, 결제 버튼 클릭 시 `sessionStorage.checkout_cart`로 복사한 뒤 `/checkout?from=cart`로 이동한다.

현재 checkout 화면에는 오래된 장바구니 항목을 다시 검증하는 로직이 있다. 그러나 사용자는 장바구니 화면에서 문제를 알지 못하고 결제 화면으로 이동한 뒤에야 상점 정보 누락이나 배송일 누락을 보게 된다.

이번 작업의 초점은 장바구니 안에서 결제 전 사고를 방지하는 것이다. 상품을 자동 삭제하거나 조용히 제외하지 않고, 문제 있는 상품을 그대로 보여 주면서 이유와 해결 행동을 제공한다.

---

## 주요 발견 문제

### P1. 장바구니 화면에서 결제 불가 상태를 알 수 없다

- `storeId`가 없거나, 일반 상품의 직접 배송·거점 픽업 항목에 `requestedDeliveryDate`가 없어도 장바구니 화면에서는 정상 상품처럼 보인다.
- 결제 화면에서야 `cartValidationError`가 표시되므로, 사용자는 결제 진입 후 흐름이 끊긴다.
- `docs/specs/frontend/consumer-stores-phase2-plan.md`의 Phase 2-S5는 과거 잘못된 장바구니 항목의 결제 차단을 요구하지만, 장바구니 화면 선제 안내는 아직 없다.

### P2. 같은 상품의 다른 선택값이 하나로 합쳐질 수 있다

- `useCart.addItem`은 `productId`만으로 기존 항목을 찾고 수량만 더한다.
- 같은 상품이라도 배송 방법이나 배송 희망일이 다르면 사용자의 구매 의도가 다르다.
- 이번 범위에서는 결제 전 방지를 먼저 적용하고, 담기 키 정교화는 후속 태스크로 분리한다.

### P3. 수량 변경에 도메인 상한이 없다

- 상품 상세에서는 공동구매 `maxPerPerson`을 고려하지만, 장바구니에서는 `+` 버튼으로 계속 증가할 수 있다.
- 현재 장바구니 항목에는 `maxPerPerson`이나 재고·슬롯 잔량 정보가 없어 장바구니 단독 상한 검증은 즉시 구현하기 어렵다.
- 이번 범위에서는 결제 불가 조건의 선제 노출을 우선하고, 수량 상한은 장바구니 항목 계약 확장 후속으로 둔다.

### P4. 다중 결제 중간 실패 시 재시도 경험이 불안정하다

- 장바구니 결제는 항목별 주문 생성과 결제를 반복한다.
- 중간 실패 시 앞선 주문은 이미 만들어졌을 수 있고, 장바구니는 남아 재시도 중복 위험이 있다.
- 이번 범위에서는 주문 생성 전 단계의 문제 항목 차단을 강화한다. 다중 결제 원자성은 별도 결제 설계가 필요하다.

### P5. 프론트 품질 경고가 남아 있다

- `cart/page.tsx`는 상품 이미지에 `<img>`를 사용해 consumer lint에서 `noImgElement` 경고가 발생한다.
- `useCart.emitChange`는 `forEach((l) => l())` 형태로 Biome 오류가 발생한다.
- 이번 범위에 포함할 수 있는 작은 품질 개선은 함께 처리하되, 전체 consumer lint의 기존 경고까지 확장하지 않는다.

---

## 개선 결정

### D1. 문제 있는 상품은 장바구니에서 삭제하지 않는다

문제 있는 상품은 장바구니 카드에 그대로 남긴다. 사용자가 담아 둔 상품이 사라졌다고 느끼지 않도록 하고, 카드 안에서 결제할 수 없는 이유를 표시한다.

### D2. 문제가 하나라도 있으면 전체 결제 버튼을 비활성화한다

장바구니 결제는 현재 전체 항목을 결제 대상으로 넘긴다. 일부 상품만 조용히 제외하면 사용자가 일부 결제를 놓칠 수 있으므로, 문제가 하나라도 있으면 전체 결제를 막는다.

### D3. 해결 행동은 상품 상세 재선택으로 제한한다

문제 상품 카드에는 `다시 선택하기` 행동을 제공하고 상품 상세로 이동시킨다. 장바구니 안에서 배송일 선택기를 재구현하지 않는다.

### D4. checkout 검증은 유지한다

장바구니 화면 검증은 사용자 경험 개선과 선제 차단이다. 저장소에 오래된 데이터가 직접 들어오거나 다른 진입이 생길 수 있으므로 checkout 화면의 기존 검증은 최종 방어선으로 유지한다.

---

## 범위

### 이번에 한다

- 장바구니 항목별 결제 가능 여부 계산.
- 결제 불가 사유 표시.
- 문제 항목이 있을 때 결제 버튼 비활성화.
- 문제 항목의 `다시 선택하기` 이동 제공.
- `sessionStorage.checkout_cart`에는 검증 통과 상태에서만 쓰기.
- 장바구니 관련 최소 lint 오류 해소.
- E2E 또는 컴포넌트 경계에서 장바구니 차단 흐름 검증 보강.

### 이번에 하지 않는다

- 장바구니 안에서 배송일 직접 수정.
- 서버 저장 장바구니 또는 계정 간 동기화.
- 다중 상품 결제의 서버 원자성 보장.
- 상품 재고·공동구매 상한을 장바구니에서 실시간 재검증.
- 같은 상품의 옵션별 병합 키 변경. 단, 후속 태스크로 명시한다.

## 장바구니 검증 규칙

| 조건 | 판정 | 화면 안내 |
| --- | --- | --- |
| `storeId` 없음 | 결제 불가 | 상점 정보가 없어 다시 담아야 한다 |
| 일반 상품이고 배송 방법이 `parcel`이 아니며 `requestedDeliveryDate` 없음 | 결제 불가 | 배송일을 다시 선택해야 한다 |
| 그 외 | 결제 가능 | 별도 안내 없음 |

공동구매는 소비자가 배송일을 고르지 않으므로 `requestedDeliveryDate` 누락만으로 차단하지 않는다. 택배는 현재 슬롯 검증 대상이 아니므로 배송일 누락만으로 차단하지 않는다.

---

## 사용자 흐름

1. 소비자가 장바구니 탭을 연다.
2. 장바구니가 저장된 항목을 읽고 항목별 결제 가능 여부를 계산한다.
3. 문제가 없는 상품은 기존처럼 상품명, 가격, 수량, 배송 희망일을 보여 준다.
4. 문제가 있는 상품은 카드 안에 사유와 `다시 선택하기` 버튼을 보여 준다.
5. 문제가 하나라도 있으면 결제 버튼은 비활성화되고, 버튼 위에 해결 안내를 표시한다.
6. 소비자가 `다시 선택하기`를 누르면 해당 상품 상세로 이동해 배송 방법·배송일을 다시 고른다.
7. 모든 문제가 해결된 뒤 결제 버튼을 누르면 현재처럼 `checkout_cart`에 복사하고 결제 화면으로 이동한다.

## 아토믹 태스크

### T1. 장바구니 검증 유틸 분리

- `CartItem`을 입력받아 결제 불가 사유 배열을 반환하는 순수 함수를 만든다.
- `storeId` 누락과 배송일 누락 조건을 checkout의 기존 조건과 맞춘다.
- 결과는 화면 표시와 결제 버튼 차단에서 같은 값을 사용한다.
- 완료 기준: 정상 상품, 상점 정보 누락, 배송일 누락, 공동구매, 택배 케이스가 함수 테스트 또는 E2E fixture에서 구분된다.

### T2. 장바구니 카드에 문제 사유 표시

- 상품 카드 안에 결제 불가 사유를 표시한다.
- 문구는 사용자가 다음 행동을 이해할 수 있게 짧게 쓴다.
- 예: `배송일을 다시 선택해야 결제할 수 있어요.`
- 완료 기준: 문제 있는 상품이 삭제되지 않고, 카드 안에 사유가 보인다.

### T3. 다시 선택하기 이동 추가

- 문제 상품 카드에 `다시 선택하기` 버튼을 추가한다.
- 이동 대상은 해당 상품 상세다.
- 상품 상세가 기존 선택 상태를 복원하지 않아도 된다. 사용자는 다시 배송 방법과 배송일을 선택한다.
- 완료 기준: 버튼 클릭 시 해당 상품 상세로 이동한다.

### T4. 결제 버튼 차단과 안내 추가

- 문제 항목이 하나라도 있으면 결제 버튼을 비활성화한다.
- 버튼 주변에 `문제 있는 상품을 다시 선택하면 결제할 수 있어요.` 수준의 안내를 표시한다.
- 비활성 상태에서는 `checkout_cart`를 쓰지 않는다.
- 완료 기준: 문제 항목이 있을 때 `/checkout?from=cart`로 이동하지 않는다.

### T5. checkout 최종 검증 유지 확인

- 장바구니 화면 검증을 추가해도 checkout의 `cartValidationError`는 제거하지 않는다.
- sessionStorage에 잘못된 값이 직접 들어간 경우 checkout에서 계속 차단한다.
- 완료 기준: checkout 직접 진입 또는 sessionStorage 조작 케이스에서 기존 차단이 유지된다.

### T6. 장바구니 프론트 품질 최소 개선

- 장바구니 상품 이미지는 Next 이미지 최적화 방식으로 바꾸거나 lint 허용 사유를 명확히 남긴다.
- `useCart.emitChange`의 Biome 오류를 제거한다.
- 완료 기준: 장바구니 관련 lint 오류가 더 이상 발생하지 않는다.

### T7. 회귀 검증 보강

- 장바구니 비어 있음, 정상 항목 결제 진입, 배송일 누락 항목 차단, 상점 정보 누락 항목 차단을 검증한다.
- 기존 인증 보호 리디렉트 테스트는 유지한다.
- 완료 기준: 장바구니 관련 테스트에서 결제 전 차단 흐름이 확인된다.

### T8. 후속 개선 후보 기록

- 같은 상품의 배송 방법·배송일별 별도 보관 키를 후속 태스크로 남긴다.
- 장바구니 안 배송일 직접 수정은 이번 범위 밖으로 남긴다.
- 다중 결제 중간 실패 보상 또는 묶음 결제는 별도 결제 설계로 넘긴다.
- 완료 기준: 후속 후보가 문서에 남아 구현 범위가 섞이지 않는다.

## 정합성 검토

### 상품 상세과의 정합성

- 상품 상세의 `장바구니`와 `바로 결제`는 `canBuy` 조건을 공유한다.
- 장바구니 화면의 검증 조건은 상품 상세에서 담기 가능한 조건과 같은 의도를 가진다.
- 단, 과거에 저장된 잘못된 항목은 상품 상세를 거치지 않았을 수 있으므로 장바구니에서 다시 검증한다.

### checkout과의 정합성

- 장바구니에서 선제 차단해도 checkout은 최종 방어선이다.
- 검증 조건은 checkout의 `cartValidationError`와 동일해야 한다.
- 장바구니와 checkout에 조건을 중복 작성하지 않도록 순수 유틸 공유를 우선 검토한다.

### 주문 API와의 정합성

- 일반 상품의 직접 배송·거점 픽업은 `requestedDeliveryDate`가 필요하다.
- 택배와 공동구매는 현재 배송 슬롯 검증 대상이 아니므로 장바구니에서 배송일 누락만으로 차단하지 않는다.
- `storeId`가 없는 항목은 `/stores/:storeId/orders` 경로를 만들 수 없으므로 반드시 차단한다.

### 저장소와의 정합성

- `greenhub_cart`는 사용자의 임시 보관소다. 검증 실패가 있어도 자동 삭제하지 않는다.
- `checkout_cart`는 결제 직전 스냅샷이다. 장바구니 검증을 통과한 경우에만 쓴다.
- checkout 성공 후 `checkout_cart`와 `greenhub_cart`를 함께 비우는 기존 계약은 유지한다.

### UX 정합성

- 문제 상품을 조용히 제외하지 않는다.
- 사용자에게 `왜 안 되는지`와 `무엇을 누르면 되는지`를 같은 카드 안에서 보여 준다.
- 전체 결제를 막는 이유는 장바구니 결제가 현재 전체 항목 스냅샷을 기준으로 동작하기 때문이다.

### 테스트 정합성

- `consumer-cart.spec.ts`는 인증 보호뿐 아니라 인증 후 장바구니 상태 검증을 포함한다.
- 오래된 장바구니 항목은 localStorage fixture로 재현한다.
- checkout 직접 방어선은 `consumer-checkout.spec.ts`에서 유지한다.

## 리스크와 완화

| 리스크 | 영향 | 완화 |
| --- | --- | --- |
| 화면이 복잡해짐 | 문제 상품이 많을 때 장바구니가 무거워 보일 수 있다 | 사유 문구를 카드 안 한 줄로 제한한다 |
| 조건 중복 | 장바구니와 checkout 조건이 어긋날 수 있다 | 검증 유틸 공유 또는 테스트 케이스 공유를 우선한다 |
| 다시 선택 후 중복 담기 | 사용자가 상품 상세에서 다시 담으면 기존 문제 항목과 새 항목이 함께 남을 수 있다 | 이번 작업에서는 문제 항목 삭제 안내를 유지하고, 병합 키 개선을 후속으로 둔다 |
| 다중 결제 실패 | 중간 결제 실패 원자성은 해결되지 않는다 | 이번 범위가 결제 전 방지임을 명시하고 별도 결제 설계로 분리한다 |
