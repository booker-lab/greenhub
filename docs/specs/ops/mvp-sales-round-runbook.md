# 디어오키드 주간 판매 회차·직배송 운영 런북

## 1. 목적과 적용 범위

이 문서는 디어오키드의 주간 회차 운영, 장애 대응, `legacy` 롤백, 수동 환불 판단 절차를 고정한다.

- 운영 프로젝트: `green-e4fe3`
- 대상 스토어: 디어 오키드
- `storeId`: `80189070-2c3d-45f2-bc11-68a870b13951`
- 출시 모드: `round_direct`
- 롤백 모드: `legacy`
- 기준 시간대: `Asia/Seoul`
- 주문 마감: 일요일 24:00, 즉 월요일 00:00
- 경매·매입: 월요일
- 직접배송: 화요일 00:00~09:00

현재 **출시 전 게이트와 작업 순서**의 정본은 `docs/memory.md`, `docs/plans/HANDOFF_mvp_round_direct_aligo_review_pause.md`, `docs/plans/PLAN_mvp_round_direct_launch_blockers.md`다. 이 런북에 남은 운영 절차가 활성 출시 PLAN의 승인·검증 게이트를 대체하지 않는다.

이 문서는 명령 실행 권한을 부여하지 않는다. 아래 명령은 절차를 설명하는 예시이며, 승인 기록 없이 실행하지 않는다. 특히 `--apply`, 환불, 문자 발송, 회차·주문 상태 변경, 파기 재실행은 별도 승인과 담당자 확인이 필요하다.

## 2. 역할과 공통 증거

| 역할 | 책임 | 기본 에스컬레이션 |
| --- | --- | --- |
| 출시 책임자 | 출시·롤백 승인, 중단 선언, 증거 묶음 확인 | 대표자와 기술 담당자 |
| 대표자·셀러 운영자 | 회차 생성·예약·마감·매입·주문 확인 | 출시 책임자 |
| 배송 책임자·기사 | 배송 시작, 보류, 사진 완료, 재배송 결과 기록 | 대표자·셀러 운영자 |
| 결제 운영자 | PortOne 원격 상태 대조, 환불 재시도 승인, 중복 환불 방지 | 출시 책임자와 기술 담당자 |
| 고객 응대 담당자 | 정보성 안내 실패 확인, 승인된 문자 재발송 결과 확인 | 대표자와 결제 운영자 |
| 개인정보·보관 담당자 | 만료 파기, 분쟁·법적 보존, 삭제 실패 확인 | 관리자와 기술 담당자 |
| 기술 담당자 | API·Firestore·Storage·외부 연동 장애 진단 | 출시 책임자 |

모든 단계는 다음 다섯 항목을 남긴다.

1. 담당 역할과 확인 시각
2. `storeId`, `roundId`, `orderId`, `paymentId`, `issueId` 중 필요한 식별자
3. 변경 전후 상태 또는 읽기 결과
4. 승인자와 승인 기록 링크
5. 다음 담당자, 재확인 시각, 중단 또는 재개 결정

고객명, 전체 전화번호, 전체 주소, 사진 원본, 서명 URL 전체값은 증거 묶음에 복사하지 않는다.

## 3. 상태를 바꾸지 않는 확인 방법

### 3.1 셀러 화면

- `/sale-rounds`: 회차 상태, KST 일정, 한도, 예약·주문 집계, `heldOrderCount` 확인
- `/orders`: 배송 보류와 확인 필요 건수 확인
- `/orders/{orderId}`: 주문 상태, 보류 사유, 재배송비, 운영 예외와 감사 기록 확인

화면의 상태는 서버 재조회가 성공한 뒤의 값만 증거로 사용한다. 브라우저에 남은 이전 화면이나 낙관적 표시를 정본으로 사용하지 않는다.

`/sale-rounds/{roundId}` 상세와 공개 회차 목록·상세는 조회 과정에서 현재 시각과 한도를
평가해 `SCHEDULED → OPEN`, `OPEN → CLOSED`, 한도 회복 시 `CLOSED → OPEN`을 반영할
수 있다. 상태 무변경 확인에는 셀러 `/sale-rounds` 목록만 사용하고 상세·공개 조회는
사용하지 않는다.

### 3.2 읽기 전용 API 예시

아래 예시는 실행하지 않은 문서용 예시다. 토큰은 세션 환경 변수로만 주입하고 명령 출력·셸 기록·문서에 남기지 않는다.

```powershell
$base = $env:GREENHUB_API_BASE_URL
$storeId = "80189070-2c3d-45f2-bc11-68a870b13951"
$headers = @{ Authorization = "Bearer $env:GREENHUB_OPERATOR_JWT" }

Invoke-RestMethod -Method Get -Uri "$base/stores/$storeId/sale-rounds" -Headers $headers
Invoke-RestMethod -Method Get -Uri "$base/stores/$storeId/orders" -Headers $headers
Invoke-RestMethod -Method Get -Uri "$base/stores/$storeId/operation-issues" -Headers $headers
Invoke-RestMethod -Method Get -Uri "$base/stores/$storeId/orders/<orderId>/payment" -Headers $headers
```

- 위 결제 경로는 로컬 `payments` 문서 조회다. PortOne 원격 재조회가 아니다.
- 운영 예외 `refresh`는 주문·로컬 결제 최신 상태를 읽지만 PortOne을 호출하지 않는다.
- 권한 오류, 응답 식별자 불일치, 손상 상태, 재조회 실패가 있으면 조치를 중단한다.

## 4. 출시 전 판매 모드 확인과 전환 게이트

### 4.1 읽기 전용 dry-run

| 항목 | 계약 |
| --- | --- |
| 담당 | 출시 책임자와 기술 담당자 2인 |
| 사전 조건 | 활성 출시 PLAN의 선행 게이트 통과, 실제 출시 대상 SHA 확정·원격 회차 E2E 통과, 운영 프로젝트·대상 스토어 재확인 |
| 예시 명령 | `node scripts/enable-dear-orchid-round-direct.mjs --dry-run` |
| 확인 증거 | 프로젝트 `green-e4fe3`, 단일 대상, 대상 `storeId`, 현재 모드, 변경 예정값, 필수 확인 플래그, 롤백 명령, 거부 조건, `외부 상태 변경: 없음 (조회만 수행)` |
| 중단 조건 | 대상 0건·다중 대상, ID·이름·소유자·활성 상태 손상, 프로젝트 불일치, 현재 모드 불명확, 배포 SHA 불일치 |
| 에스컬레이션 | 기술 담당자가 원인을 확인하고 새 dry-run 증거를 만든 뒤 출시 책임자가 재승인 |

`salesMode` 미설정 또는 `null`은 호환 현재값 `legacy`로만 판독한다. 스크립트 표준 출력은
`updateTimeMillis`를 표시하지 않으므로, 별도 읽기 전용 감사로 수집하지 않은 시각을
dry-run 증거로 추정해 기록하지 않는다.

### 4.2 실제 `round_direct` 전환

다음 조건을 모두 충족하고 별도 사용자 승인을 받은 경우에만 가능하다.

- 활성 출시 PLAN이 요구하는 ALIGO 승인·실제 발송 검증, 실제 출시 대상 SHA 원격 E2E, 운영 설정·배포·smoke가 모두 통과했다.
- 같은 배포 SHA에서 dry-run이 `legacy → round_direct` 단일 대상을 출력했다.
- 첫 회차가 `SCHEDULED`이며 상품·가격·한도·KST 일정·이천시 지역이 검수됐다.
- 셀러·기사 계정과 고객 응대·결제 담당자가 근무 가능하다.
- `OPEN` 운영 예외가 없거나 출시 책임자가 각각의 영향과 담당자를 승인했다.
- 롤백 담당자와 롤백 명령이 준비됐다.

승인 후에만 사용할 예시:

```powershell
node scripts/enable-dear-orchid-round-direct.mjs --apply --target-mode=round_direct --confirm=80189070-2c3d-45f2-bc11-68a870b13951:legacy:round_direct
```

실행 결과의 대상·현재값·변경값이 승인 기록과 하나라도 다르면 즉시 중단한다. 스크립트 외 Firestore Console 직접 편집은 허용하지 않는다.

## 5. 주간 표준 운영

### 5.1 회차 생성과 상태별 확인

| 단계 | 담당·사전 조건 | 확인 증거 | 중단 조건·에스컬레이션 |
| --- | --- | --- | --- |
| 생성 `DRAFT` | 대표자·셀러 운영자. 이전 회차와 이번 주 상품 정본 준비 | 새 `roundId`, 상품 중복 없음, 회차 가격·상품별 한도, 이천시 활성 지역, 일정 순서 | 상품·가격·시간대 불명확 시 저장·예약 중단 후 대표자 확인 |
| 예약 `SCHEDULED` | 대표자. 주문 시작 < 주문 마감 <= 경매 < 배송 시작 < 배송 종료 | `schedule.timezone=Asia/Seoul`, 일요일 24:00 마감, 월요일 경매, 화요일 00:00~09:00 배송 | 과거 시각, 일정 역전, 잘못된 지역·한도, 링크 오노출 시 예약 중단 후 기술 담당자 확인 |
| 판매 `OPEN` | 셀러 운영자. 공개 링크와 결제 준비 확인. 서버가 `orderOpenAt <= now < orderCloseAt`을 확인 | 공개 회차·상품 조회, 가격, `closeReason=null`, 예약·주문 집계, 당근 링크, authoritative 시작 window | 시작 전 수동 `OPEN`, 가격·상품·지역 불일치, 결제 오류 증가, 비회차 판매 방식 노출 시 신규 유입 중단과 롤백 판단 |
| 마감 `CLOSED` | 대표자. 일요일 24:00 또는 수동·한도 마감 | `closeReason=SCHEDULE_ENDED|CAPACITY|MANUAL`, 신규 주문 차단, `PENDING`·결제 조회 예외 목록 | 마감 뒤 신규 예약, 결제 상태 불명확, 카운터 불일치 시 매입 확정 중단 후 기술·결제 담당자 확인 |
| 완료 `COMPLETED` | 대표자. 모든 주문 종결과 확인 필요 점검 완료 | 모든 회차 주문이 `DELIVERED|REVIEWED|CANCELLED`, `heldOrderCount=0`, 관련 `OPEN` 예외 검토 | 미완료·보류 주문은 서버가 거부. 관련 `OPEN` 예외나 사진·환불·연락 증거 누락 시 운영 정책상 완료 시도 중단 |

`CAPACITY`로 닫힌 회차는 주문 마감 전 확보량이 반환되면 자동으로 `OPEN` 복귀할 수 있다. `SCHEDULE_ENDED` 또는 `MANUAL` 마감은 자동 재개되지 않는다. 수동 `SCHEDULED → OPEN`은 서버가 authoritative `orderOpenAt <= now < orderCloseAt`을 확인한 경우에만 허용한다. 상태 변경 직전에는 항상 재조회한다.

회차 편집은 `DRAFT|SCHEDULED`의 fresh 상태와 item snapshot을 같은 write transaction에서 재확인해야
한다. `OPEN` 전환·예약·배송 주문과 경합해 어느 상태인지 확정할 수 없거나 item 사용량이 이미
존재하면 저장을 중단하고 기술 담당자에게 전달한다. `CANCELLING` 저장 뒤 process interruption은
현재 owner·lease·expiry 기반 deterministic recovery가 직접 검증된 상태가 아니므로,
Firestore를 직접 `CANCELLED`로 고치거나 주문을 임의 정리하지 않는다.

### 5.2 일요일 주문 마감

| 항목 | 계약 |
| --- | --- |
| 담당 | 대표자·셀러 운영자, 결제 운영자 |
| 사전 조건 | 회차가 `OPEN`, 마감 시각과 한도 집계 확인 |
| 절차 | 월요일 00:00 KST 직후 재조회 → `CLOSED`와 `closeReason` 확인 → `PENDING` 주문과 `PAYMENT_LOOKUP_FAILED` 분리 → 확정 주문 수량·배송지 수 집계 |
| 확인 증거 | 회차 상태·마감 사유·카운터, 주문 상태별 건수, 확인 필요 목록 |
| 중단 조건 | `OPEN` 지속, 마감 뒤 신규 예약, PortOne·로컬 상태 불일치, 카운터 음수·한도 초과 |
| 에스컬레이션 | 매입 수량 확정을 멈추고 결제 운영자와 기술 담당자에게 전달 |

### 5.3 월요일 경매·매입

| 항목 | 계약 |
| --- | --- |
| 담당 | 대표자·매입 담당자 |
| 사전 조건 | 회차 `CLOSED`, 불명확 결제 0건 또는 개별 보류 승인 |
| 절차 | 확정 주문의 상품별 수량 집계 → 경매 매입 → 검수·포장 → 주문을 준비 상태로 처리 → 배송 순서와 기사 배정 확인 |
| 확인 증거 | 상품별 확정 수량, 실제 매입 수량, 부족·대체 판단, 포장 완료 주문 목록 |
| 중단 조건 | 결제 불명확, 수량 집계 불일치, 품질·재고 부족, 기사·배송 경로 미확정 |
| 에스컬레이션 | 대표자가 부분 취소·환불 필요성을 판단하고 결제 운영자에게 주문 단위로 전달 |

결제 상태를 추정해 매입하지 않는다. 주문 목록의 로컬 상태만으로 PortOne 승인 여부를 단정하지 않는다.

### 5.4 화요일 00:00~09:00 직접배송

| 항목 | 계약 |
| --- | --- |
| 담당 | 배송 책임자·담당 기사 |
| 사전 조건 | 회차 `CLOSED`, 주문 `PREPARING`, 담당 기사·배송 순서·연락 수단 확인 |
| 절차 | 담당 주문만 `DELIVERING` 시작 → 배송 또는 보류 기록 → 성공 시 JPEG 사진을 서버 API로 업로드 → 서버가 `DELIVERED`를 반환한 건만 완료 집계 |
| 확인 증거 | 주문별 상태, 보류 스냅샷, 연결 `photoId`, 완료 시각 |
| 중단 조건 | 다른 기사 주문, 회차 직배송 아님, 상태 불일치, 사진 없는 완료, 서버 응답 식별자 불일치 |
| 에스컬레이션 | 해당 주문만 중단하고 배송 책임자와 기술 담당자에게 전달. 다른 안전한 주문은 계속 처리 |

09:00에 모든 주문을 재조회한다. 미완료·보류·사진 실패 주문을 별도 목록으로 고정하고 회차 완료를 시도하지 않는다.

## 6. 장애와 운영 예외

### 6.1 결제 상태 불명확

1. 담당: 결제 운영자.
2. 사전 조건: `PENDING`이 15분 이상 지속되거나 `PAYMENT_LOOKUP_FAILED`가 `OPEN`.
3. 로컬 주문·결제 상태와 PortOne 관리자 콘솔의 동일 `paymentId`를 각각 조회한다.
4. 금액, 상태, 거래 식별자, 승인·취소 시각을 대조한다.
5. 확인 증거에는 상태·시각·식별자만 남기고 PortOne 인증 정보나 전체 응답은 남기지 않는다.
6. PortOne이 `PAID`인데 로컬 확정이 아니면 주문 취소·환불을 임의 실행하지 않고 기술 담당자에게 재조정 요청한다.
7. PortOne이 결제 없음으로 명확히 확인된 경우에만 자동 timeout 결과와 일치하는지 확인한다.

`PAYMENT_LOOKUP_FAILED`에는 현재 운영 화면의 자동 조치가 없다. 상태를 추정해 `DISMISSED` 또는 해결 처리하지 말고 기술 담당자에게 에스컬레이션한다.

### 6.2 늦은 결제와 자동 환불 실패

- timeout 뒤 PortOne `PAID`가 확인되면 서버는 회차 한도 재확보를 시도한다.
- 재확보 성공 시 기존 주문을 확정 흐름으로 계속 처리한다.
- 재확보 실패 시 전액 환불하고 로컬 결제를 `CANCELLED`로 기록하는 것이 정상 수렴이다.
- PortOne은 환불됐지만 로컬 상태가 다르거나, 늦은 결제 환불 호출 자체가 실패한 흔적이 있으면 수동 환불을 바로 반복하지 않는다.
- 열린 `AUTO_REFUND_FAILED`만 최신 상태 재조회 후 `RETRY_REFUND` 대상이 될 수 있다.
- 늦은 결제 직접 환불 실패는 현재 구현에서 항상 `AUTO_REFUND_FAILED`로 수렴한다고 보장되지 않는다. 해당 불일치는 최우선 결제 장애로 기술 담당자에게 전달한다.

### 6.3 고객 안내 최종 실패

정상 자동 경로는 알림톡 최대 3회 후 동일 내용 문자 1회다. 모두 실패하면 주문 상태를 유지하고 `CUSTOMER_NOTICE_FAILED`를 연다.

| 항목 | 계약 |
| --- | --- |
| 담당 | 고객 응대 담당자 |
| 사전 조건 | 예외가 `OPEN`, 주문이 아직 `DELIVERED|CANCELLED`가 아님 |
| 절차 | 주문·예외 `refresh` → 허용 조치가 계속 `RESEND_SMS`인지 확인 → 승인 후 1회 실행 → 별도 SMS 감사 기록과 `RESOLVED` 확인 |
| 확인 증거 | `issueId`, 템플릿 코드, 조치 상태, 시도 시각. 전화번호·본문 원문 제외 |
| 중단 조건 | 예외가 닫힘, 주문 완료·취소, 연락처 손상, 조치 진행 중, 응답 식별자 불일치 |
| 에스컬레이션 | 주문 완료·취소 뒤에도 예외가 `OPEN`이면 현재 API로 종결하지 말고 관리자·기술 담당자에게 전달 |

개인 휴대전화나 승인되지 않은 외부 문자 도구로 우회 발송하지 않는다.

### 6.4 배송 보류·재배송비·2차 배송 실패

배송 실패는 주문을 임의 완료·취소하지 않고 `DELIVERY_HELD`로 전환해 아래 원인과 후속
일정을 기록한다.

| 원인 | 운영 계약 |
| --- | --- |
| `WEATHER` | 판매자 책임, 재배송비 없음, 새 배송 시각 필수. 즉시 안내 후 새 일정으로 재개 |
| `ACCESS_UNAVAILABLE|ADDRESS_ISSUE|CUSTOMER_UNREACHABLE|OTHER` | 실제 원인과 책임을 기록. 고객 책임이면 다음 연락·배송 시각과 양수 재배송비를 확인 |
| 첫 고객 사유 실패 | 주문자 본인만 멱등 키로 재배송비 1건 생성·결제. 결제 전 재배송 금지 |
| 유료 재배송 실패 | 자동 환불 판단 금지. `REDELIVERY_FAILED`, `requiresOperationalReview`를 확인하고 상품 상태·재판매 가능성·고객 연락 기록을 대표자에게 전달 |

보류 해소는 셀러가 `PREPARING|CANCELLED`, 담당 기사가 `DELIVERING`으로만 수행한다. `REDELIVERY_FAILED`에는 자동 조치가 없으므로 환불이나 문자 조치를 임의로 연결하지 않는다.

### 6.5 배송 사진 업로드·권한·서명 URL

- 회차 직배송 사진은 담당 기사가 `DELIVERING` 주문에 JPEG, 최대 5MiB로 서버 업로드한다.
- 서버 비공개 정본 경로는 `deliveryPhotos/{orderId}/{photoId}.jpg`이며 클라이언트가
  이 경로를 직접 읽거나 쓰지 않는다.
- 같은 재시도는 같은 `idempotencyKey`와 같은 JPEG를 사용한다. 같은 키로 다른 사진을 덮어쓰지 않는다.
- 서버가 사진 연결과 `DELIVERED`를 모두 반환한 뒤에만 성공으로 기록한다.
- 사진 없는 직접 완료, Firebase Storage 직접 업로드, 공개 URL 저장을 금지한다.
- 읽기 URL은 주문자 본인, 스토어 소유자, 담당 기사, 관리자에게만 15분 동안 발급된다.
- 서명 URL 장애 시 원본 경로나 공개 URL로 우회하지 않는다. 권한·주문 상태·연결 `photoId`를 재확인하고 GET 재시도 후 기술 담당자에게 전달한다.
- 증거에는 URL 전체값과 쿼리 서명을 남기지 않고 `photoId`, 발급 성공 여부, 만료 시각만 기록한다.

### 6.6 회차 완료 거부와 확인 필요 점검

서버의 하드 거부 조건은 `heldOrderCount > 0` 또는 상태가 `DELIVERED|REVIEWED|CANCELLED`가 아닌 회차 주문 존재다.

운영자는 추가로 다음을 모두 확인한 뒤에만 완료한다.

- `PAYMENT_LOOKUP_FAILED`, `AUTO_REFUND_FAILED`, `CUSTOMER_NOTICE_FAILED`, `REDELIVERY_FAILED` 관련 `OPEN` 예외 검토
- 모든 `DELIVERED` 회차 주문의 연결 사진 증거
- 고객 책임 재배송비의 `PAID|CANCELLED|REFUNDED` 최종 상태
- 취소 주문의 본 결제와 재배송비 환불 상태
- 09:00 미완료 주문의 후속 담당자·일정

운영 예외는 회차 완료 API의 직접 하드 블로커가 아니므로, 관련 `OPEN` 예외가 남으면 운영 정책상 완료 요청을 중단한다.

### 6.7 기록 보관·파기 실패

- 정기 파기는 매일 03:00 KST에 만료 기록을 조회한다.
- 배송 사진 90일, 마케팅 동의 3년, 환불·분쟁·고객응대 3년, 계약·결제·공급 5년을 적용한다.
- `disputeStatus=OPEN` 또는 `legalHold=true`는 파기하지 않는다.
- Storage 삭제는 최대 3회 시도하며 최종 실패 시 보관 문서를 유지하고 `RETENTION_DELETE_FAILED`를 연다.
- 실패한 원본을 수동 삭제하거나 보관 문서만 먼저 삭제하지 않는다.
- 현재 `RETENTION_DELETE_FAILED`에는 자동 운영 조치가 없고, 배송 사진 failure는 store identity가
  없어 일부 기록이 스토어 범위 목록에 나타나지 않을 수 있으며 current API에서 global retention
  queue도 확인되지 않았다. 이를 확인 완료로 간주하거나 원본·보관 문서를 임의 삭제하지 말고,
  `RETENTION-DELETE-ISSUE-ROUTING`에 따라 기술 담당자에게 전달한다.
- 같은 원인의 재시도는 다음 승인된 정기 작업 또는 기술 담당자의 복구 절차로만 수행한다.

## 7. 소비자 장애 시 `legacy` 롤백

### 7.1 롤백 판단

다음 중 하나면 출시 책임자가 신규 회차 유입 중단과 롤백을 판단한다.

- 회차 상품·가격·마감이 잘못 노출됨
- 주문 생성·단일 결제 실패가 반복됨
- 이천시 외 주문 또는 한도 초과가 허용됨
- 기존 legacy 화면과 회차 화면이 혼합됨
- 결제 상태 불명확 또는 5xx가 연속 발생함
- 개인정보·사진 권한 경계 이상이 의심됨

보안·개인정보 의심은 영향 건수와 무관하게 즉시 중단한다.

### 7.2 롤백 절차

실제 롤백 승인 전에 다음 읽기 전용 예시로 현재값 `round_direct`, 예정값 `legacy`,
프로젝트와 단일 대상을 먼저 확인한다.

```powershell
node scripts/enable-dear-orchid-round-direct.mjs --dry-run --target-mode=legacy
```

| 항목 | 계약 |
| --- | --- |
| 담당 | 출시 책임자 승인, 기술 담당자 실행 |
| 사전 조건 | 현재 모드 `round_direct`, 대상·프로젝트 단일 확인, 이미 결제된 주문 목록 고정 |
| 예시 명령 | `node scripts/enable-dear-orchid-round-direct.mjs --apply --target-mode=legacy --confirm=80189070-2c3d-45f2-bc11-68a870b13951:round_direct:legacy` |
| 확인 증거 | 실행 결과 `round_direct → legacy`, 소비자 신규 회차 진입 차단, 기존 주문 조회 가능 |
| 중단 조건 | 대상·현재 모드·프로젝트 불일치, 승인 누락, 기존 주문 조회 불가 |
| 에스컬레이션 | Firestore 직접 수정 금지. 기술 담당자가 원인을 확인하고 출시 책임자가 새 절차 승인 |

### 7.3 롤백 뒤 이미 결제된 회차 주문

- 회차·주문·결제·사진 데이터를 삭제하거나 legacy 주문으로 변환하지 않는다.
- `salesMode`는 소비자 신규 진입 게이트이며 기존 `schemaVersion: 2` 주문 수명주기를 바꾸지 않는다.
- 셀러는 회차 주문을 계속 매입·준비하고, 담당 기사는 기존 회차 직배송 주문을 배송·보류·사진 완료한다.
- 결제·환불·알림·재배송·보관 예외는 본 런북의 동일 절차로 처리한다.
- 장애가 기존 주문 처리 화면에도 영향을 주면 주문별 수기 상태 변경 대신 기술 담당자가 API 복구를 우선한다.
- 원인 수정 뒤 활성 출시 PLAN이 요구하는 실제 출시 대상 SHA의 핵심 E2E와 새 dry-run을 다시 통과하기 전 `round_direct`를 재활성화하지 않는다.

## 8. 수동 환불과 중복 방지

### 8.1 필수 사전 조회

1. 결제 운영자와 승인자 2인이 주문·결제·운영 예외 식별자를 확인한다.
2. `GET /stores/{storeId}/orders/{orderId}`로 주문 최신 상태를 확인한다.
3. `GET /stores/{storeId}/orders/{orderId}/payment`로 로컬 결제를 확인한다.
4. PortOne 관리자 콘솔에서 같은 `portonePaymentId`를 원격 재조회한다.
5. 주문 금액, 원격 상태, 로컬 상태, 기존 `refundedAt`, `refundAmount`, 열린 환불 claim·예외를 대조한다.
6. 재배송비가 있으면 본 결제와 `orderCharges`를 별개 결제로 대조한다.

다음이면 즉시 중단한다: 원격 조회 실패, 금액 불일치, 이미 전액 취소·환불, 다른 조치 진행 중, 주문·결제 식별자 불일치, 재배송비 상태 불명확.

### 8.2 애플리케이션 환불 재시도

우선 경로는 열린 `AUTO_REFUND_FAILED`의 서버 조치다.

1. 운영 예외 `refresh`로 주문·로컬 결제 상태를 재확인한다.
2. 허용 조치가 `RETRY_REFUND`인지 확인한다.
3. 별도 승인 뒤 한 번만 실행한다.
4. 서버는 5분 claim으로 정상 동시 실행을 막고, 로컬 결제가 이미 `REFUNDED|CANCELLED`면 외부 환불을 반복하지 않는다. lease 만료 뒤 takeover와 stale worker fencing은 현재 직접 검증되지 않았으므로, 호출 결과나 소유권이 불명확하면 자동 재시도하지 않고 기술 담당자에게 전달한다.
5. `SUCCEEDED` 감사 기록, 예외 `RESOLVED`, PortOne 취소 상태, 로컬 `CANCELLED`를 모두 확인한다.

실패하면 같은 버튼을 연속 클릭하지 않는다. `FAILED` 감사 기록과 실패 시각을 남기고 결제 운영자·기술 담당자에게 전달한다.

### 8.3 PortOne 콘솔 수동 환불

애플리케이션 재시도가 불가능하고 출시 책임자와 결제 운영자가 별도 승인한 최후 수단이다.

- 실행 직전에 PortOne을 다시 조회한다.
- 정확한 결제 한 건과 승인 금액 이하만 취소한다.
- 본 결제와 재배송비 결제를 혼동하지 않는다.
- 취소 성공 후 같은 주문에 `RETRY_REFUND`를 실행하지 않는다.
- PortOne 성공·로컬 미반영 상태를 기술 담당자에게 전달해 로컬 결제·주문·법정 분쟁 기록을 재조정한다.
- 재조정 완료 전 주문을 임의 `CANCELLED`로 바꾸거나 운영 예외를 닫지 않는다.

## 9. 로그·개인정보·비밀정보 규칙

허용되는 로그 필드는 식별자, 상태, 건수, 시각, 정제된 오류 유형, HTTP 상태다.

다음을 로그·이슈·스크린샷·채팅·문서에 남기지 않는다.

- `FIREBASE_SERVICE_ACCOUNT_JSON`, 서비스 계정 파일 내용, private key
- `PORTONE_V2_SECRET`, `PORTONE_WEBHOOK_SECRET`, 웹훅 서명과 raw body
- JWT, `Authorization` 헤더, 쿠키, 세션 토큰
- 전체 전화번호·주소·고객명·알림 본문
- 배송 사진 원본, Storage 경로가 포함된 공개 링크, 서명 URL 전체값
- PortOne 전체 응답이나 외부 오류에 포함된 인증 문자열

오류 메시지는 줄바꿈을 제거하고 300자 이내의 정제된 요약으로 남긴다. 전화번호는 필요 시 끝 4자리도 운영 문서에는 남기지 않고 권한 있는 화면에서만 대조한다.
