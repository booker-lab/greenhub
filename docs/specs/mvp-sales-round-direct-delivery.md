# MVP 주간 판매 회차·직배송 구현 명세

## 목적

디어오키드 MVP는 기존 택배·거점픽업·공동구매 로직을 유지하면서 `round_direct` 판매 모드에서만 주간 판매 회차와 이천시 직접배송 주문 경로를 사용한다. 이 문서는 `docs/plans/PLAN_mvp_sales_round_direct_delivery.md`, `docs/discussions/DISCUSS_mvp_sales_focus.md`, `docs/CRITICAL_LOGIC.md` #CL-166의 API·화면·보관 계약을 구현 기준으로 고정한다.

## 범위

- `Store.salesMode`가 없거나 `legacy`이면 기존 주문 생성·조회·결제·배송 의미를 유지한다.
- `Store.salesMode === 'round_direct'`인 디어오키드 소비자 화면에서만 회차 상품, 단일 장바구니, 단일 결제, 화요일 직접배송 흐름을 노출한다.
- 기존 주문 데이터는 새 구조로 일괄 변환하지 않고 조회 계층에서 주문 상품 1개로 정규화한다.
- 당근 비즈니스는 유입 채널로만 사용하며 주문·결제·배송 상태의 정본은 그린러브에 둔다.

## 도메인 데이터 계약

### `saleRounds`

- 한 주의 판매·경매·배송 운영 단위다.
- 상태는 `DRAFT → SCHEDULED → OPEN → CLOSED → COMPLETED` 순서이며 대표자 취소는 `CANCELLED`로 기록한다.
- 필수 필드는 `storeId`, `status`, `name`, 주문 시작·마감 시각, 경매일, 배송 시작·종료 시각, 활성 배송 지역, 배송지 한도, 상품 수량 한도, 주문·예약 집계다.
- 주문 마감 시각 또는 배송지·상품 한도 중 먼저 도달한 조건에 따라 `CLOSED`로 전환한다.
- `DELIVERY_HELD` 주문이 남아 있으면 `COMPLETED` 전환을 거부한다.

### `saleRoundItems`

- 회차에 포함된 상품 항목이며 상품 원본을 복제하지 않는다.
- 필수 필드는 `roundId`, `productId`, 상품명·대표 이미지 스냅샷, 회차 가격, 회차별 판매 한도, 노출 순서, 예약·주문 수량이다.
- 상품 원본 또는 다음 회차 가격이 바뀌어도 과거 주문 스냅샷과 환불 기준 금액은 바뀌지 않는다.

### `checkoutReservations`

- 고객이 결제를 시작할 때 배송지 1곳과 주문 상품 수량 합계를 15분간 임시 확보한다.
- 장바구니 단계에는 적용하지 않고 결제 시도에만 적용한다.
- 상태는 `HELD`, `CONSUMED`, `RELEASED`, `EXPIRED`를 사용한다.
- 결제 실패, 고객 취소, 만료 시 확보량을 즉시 반환한다.
- 15분 이후 늦은 결제가 확인되면 서버가 회차 상태와 한도를 재검증하고, 수용 불가 시 포트원 취소 API로 전액 환불한다.

### `orders`

- 신규 회차 주문은 `schemaVersion: 2`, `roundId`, 주문 상품 스냅샷 배열, 유입 스냅샷, 배송 연락용 전화번호를 가진다.
- 주문 전체는 하나의 배송 상태로 관리하며 `DELIVERY_HELD`는 `PREPARING` 또는 `DELIVERING`에서 진입한다.
- 배송 보류에는 발생 시각, 사유, 고객 책임 여부, 재배송비, 다음 안내 예정일, 연락 이력을 기록한다.
- 고객은 주문 마감 전까지 MY에서 직접 취소할 수 있고, 취소 완료 시 회차 한도를 복구한다.
- 주문 마감 후 고객 직접 취소는 막고 대표자가 매입 여부와 상품 상태를 확인해 처리한다.

### `orderCharges`

- 고객 사유 첫 배송 실패 후 1회 유료 재배송비 결제를 관리한다.
- 재배송비 결제는 주문 본 결제와 분리하고, 같은 사유에 대해 중복 청구되지 않도록 멱등 키를 사용한다.
- 유료 재배송까지 실패하면 자동 환불 판단을 하지 않고 `operationIssues`로 이관한다.

### `operationIssues`

- 결제 재조회 실패, 자동 환불 실패, 알림톡·문자 최종 실패, 유료 재배송 실패 같은 수동 조치 대상을 관리한다.
- 같은 원인의 예외는 멱등 키로 하나의 열린 항목에 합친다.
- 조치 실행 전 최신 결제·주문 상태를 다시 검증하고, 담당자·시각·결과·실패 사유를 감사 기록으로 남긴다.

## API 계약

### 공개 소비자 API

- 현재·지난 회차 조회는 `OPEN`, `SCHEDULED`, `CLOSED`, `COMPLETED` 중 소비자 노출 가능한 회차와 회차 상품을 반환한다.
- 상품 상세는 `round` 파라미터가 있으면 해당 회차 상품과 구매 가능 상태를 함께 반환한다.
- 장바구니 검증 API는 회차 상태, 가격, 판매 가능 수량, 이천시 배송 가능 여부를 서버 기준으로 재검증한다.
- 주문 생성 API는 같은 회차의 주문 상품 배열, 배송 주소, 배송 연락용 전화번호, 선택 마케팅 동의, 당근 유입 값을 받는다.
- 고객 취소 API는 주문 마감 전 주문만 허용하고 결제 환불과 한도 반환을 함께 수행한다.

### 셀러 API

- 셀러는 회차 목록 조회, 회차 생성·수정, 이전 회차 복사, 상태 전환, 당근용 링크 조회를 수행한다.
- 회차 편집은 주문 기간, 경매일, 배송 시간, 활성 배송 지역, 배송지 한도, 상품 수량 한도, 포함 상품과 회차 가격을 한 요청 단위로 검증한다.
- 회차 완료 전환은 배송 보류 주문이 없는지 확인한다.
- `확인 필요` API는 결제 재조회, 환불 재시도, 문자 재발송, 고객 전화 연결 기록, 수동 해결 처리를 제공한다.

### 드라이버 API

- 직접배송 대상 주문만 보드에 노출한다.
- 배송 완료 전 사진 업로드를 요구하며 클라이언트가 Firebase Storage에 직접 쓰지 않는다.
- 배송 보류는 사유, 고객 책임 여부, 다음 연락·배송 예정일과 함께 기록한다.

### 결제·알림 API

- 포트원 웹훅은 주문 확정, 한도 소비, 알림 발송을 각각 멱등 처리한다.
- 결제 타임아웃은 포트원 상태를 서버에서 재조회한 뒤 주문 확정, 예약 반환, 한도 재확보 또는 자동 환불 중 하나로 닫는다.
- 알림톡은 최대 3회 재시도하고 실패 시 같은 내용을 문자로 대체한다.
- 문자 대체도 실패한 경우에만 주문 상태를 유지한 채 `operationIssues`에 `고객 안내 실패`를 만든다.

## 소비자 화면 계약

- 홈은 현재 회차, 주문 마감, `화요일 오전 9시까지 문 앞 배송`, 지난 회차 순으로 구성한다.
- 상품 목록은 현재·지난 회차의 호접란만 노출한다.
- 하단 내비게이션은 홈, 상품, 장바구니, MY 네 항목만 둔다.
- 공동구매 직접 진입은 `round_direct`에서 홈으로 돌린다.
- 상품 상세와 결제 직전 화면에는 `경기도 이천시 직접배송`, 마감 시각, 회차 가격, 기상 연기 원칙, 청약철회 제한 조건을 명확히 표시한다.
- 결제 화면의 마케팅 수신 동의는 기본 해제 상태이며 배송 연락용 전화번호와 분리한다.
- 주문 목록과 상세는 다중 상품 대표명, 배송 보류, 재배송비 결제, 배송 완료 사진, 마감 전 취소 상태를 표시한다.

## 셀러·드라이버 화면 계약

- 셀러 하단 메뉴에는 주문, 회차, 상품, 준비, 설정을 둔다.
- 회차 목록은 작성 중, 판매 예정, 판매 중, 주문 마감, 배송 완료 상태와 주문·판매 수량을 보여준다.
- 회차 편집 화면은 이전 회차 복사와 당근 대표·상품 링크 복사를 제공한다.
- 셀러 주문 화면은 배송 보류와 확인 필요 건수를 업무 우선순위로 보여준다.
- 드라이버 보드는 직접배송 주문만 다루며, 완료 사진 촬영과 보류 사유 기록을 필수 흐름으로 둔다.

## 보관·보안 계약

- 주문 당시 주소·전화번호, 계약·결제·공급 기록은 `legalOrderRecords`에 5년 보관한다.
- 환불, 분쟁, 고객응대 기록은 `legalDisputeRecords`에 3년 보관한다.
- 마케팅 동의·철회 증거는 `marketingConsentLogs`에 철회 후 3년 보관하며 광고 대상 선정에는 사용하지 않는다.
- 배송 완료 사진은 비공개 `deliveryPhotos/{orderId}/{photoId}.jpg` 경로에 서버 업로드하고 기본 90일 후 삭제한다.
- 분쟁 중인 기록과 사진은 해결 시까지 보관 연장할 수 있다.
- 법정 보관 컬렉션과 배송 사진 원본은 소비자앱·드라이버앱·일반 셀러 권한에서 직접 접근할 수 없다.
- 각 보관 기록은 파기 예정 시각을 가지며 정기 작업이 만료 기록과 연결 Storage 파일을 영구 삭제한다.

## 검증 기준

- `legacy` 스토어의 기존 주문 생성·조회·상태 변경은 회귀하지 않아야 한다.
- `round_direct` 주문은 한 회차의 여러 상품을 한 주문과 한 결제로 묶어야 한다.
- 이천시 밖 주소, 마감 회차, 한도 초과, 가격·수량 변경은 결제 전에 차단하거나 고객 재확인을 요구해야 한다.
- 늦은 결제, 중복 웹훅, 자동 환불 실패, 알림 최종 실패, 배송 보류, 사진 권한은 테스트로 고정해야 한다.
- 모든 구현 Task는 PLAN의 Dependency 순서와 단일 Target 원칙을 따른다.
