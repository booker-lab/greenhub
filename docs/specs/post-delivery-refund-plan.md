## 업무 요약 (협업용)

### 무엇이 문제인가

꽃을 받은 손님이 "꽃이 상했어요"라고 연락해도 지금은 **앱 안에서 환불할 방법이 없다.** 배송이 시작되면 판매자도 관리자도 취소 버튼을 쓸 수 없다. 그래서 결제 회사(PortOne) 화면에서 직접 돈을 돌려줘야 한다. 그러면 앱에는 주문이 "배송 완료"로 남고, 판매자 정산금도 그대로 나가서 **기록과 실제 돈이 어긋난다.**

판매자 주문 화면은 "소비자 반품 신청으로 처리된다"고 안내하지만, **그런 기능은 없다.**

### 함께 확정한 것

1. **판매자가 직접 환불한다.** 일반 쇼핑몰(스마트스토어 등)과 같은 구조다. 관리자도 같은 환불을 할 수 있다(예비 경로).
2. **손님 요청은 전화·카카오 채널로 받는다.** 앱에 "환불 요청" 버튼은 이번에 만들지 않는다.
3. **환불은 전액만 한다.** 부분 환불은 나중에 다시 검토한다.
4. **판매자는 배송 완료 후 7일까지만 직접 환불할 수 있고, 그 뒤는 관리자가 처리한다.** 법상 손님은 상품이 약속과 다르면 받은 날부터 3개월(안 날부터 30일)까지 환불을 요구할 수 있다. 그래서 관리자 경로에는 기한을 두지 않는다. 7일은 손님 권리의 기한이 아니라 **판매자가 혼자 처리하는 기간**이다.
5. **증빙은 사유 선택과 메모를 필수로 남긴다.** 사유는 꽃 상함·파손·잘못 배송·기타 중에서 고른다. 사진은 카카오 채널 대화에 남기고 앱에는 올리지 않는다.
6. **정산 지급 가능 시점을 배송 완료 7일 뒤로 늦춘다**(지금은 다음 날). 스마트스토어의 "구매확정 후 정산"과 같은 방식이다. 판매자가 환불하는 7일 동안에는 돈이 아직 나가지 않으므로 정산을 취소하기만 하면 된다.
7. **7일이 지나 관리자가 환불했는데 정산금이 이미 나갔다면**, 정산 화면에 **"돌려받을 돈 ○○원"**을 표시한다. 관리자가 판매자에게 계좌로 받은 뒤 **"회수 완료"**를 누른다. 다음 정산에서 자동으로 빼는 기능은 만들지 않는다.
8. **손님 알림은 이미 심사를 통과한 "주문 취소" 카카오 알림을 그대로 쓴다.** 사유 칸에는 서버가 정한 문구가 들어간다(예: "꽃 상태 문제로 전액 환불"). 새 알림 심사는 하지 않는다.
9. **11월 1일 파일럿 전에 여는 것을 목표로 하고, 손으로 처리하는 임시 절차를 먼저 만든다.**

### 하지 않기로 한 것

- 손님이 앱에서 직접 환불을 요청하는 버튼과 판매자의 요청 목록
- 부분 환불(금액 입력, 상품 단위 선택)
- 증빙 사진 업로드와 저장
- 다음 정산에서 자동으로 빼는 기능
- 새 카카오 알림 문구 심사

### 잘 됐다고 말할 때 확인하는 것

판매자가 배송 완료 3일째 주문에서 "배송 후 환불"을 누르면 다음이 함께 맞아야 한다. **손님 카드 결제가 취소되고, 손님에게 취소 알림이 가고, 주문은 "취소"로, 그 주문의 정산은 "취소"로 바뀐다.** 판매자는 결제 회사 화면을 한 번도 열지 않는다.

### 손님·판매자에게 기대되는 변화

- 판매자: 주문 상세 화면에 "배송 후 환불" 버튼이 생긴다(배송 완료 후 7일까지). 7일이 지나면 "관리자에게 문의" 안내가 보인다.
- 관리자: 주문에 기한 없는 "배송 후 환불" 버튼이 생기고, 정산 화면에 "돌려받을 돈" 표시와 "회수 완료" 버튼이 생긴다.
- 손님: 카카오톡으로 "주문이 취소되었습니다. 사유: 꽃 상태 문제로 전액 환불"을 받고, 카드사 일정에 따라 돈을 돌려받는다.
- 판매자 정산금은 지금보다 **6일 늦게** 지급 가능해진다.

## 2. 규칙 (구현이 지켜야 할 것)

### 2.1 누가, 언제

| 누가 | 주문 상태 | 기간 | 정산 상태 조건 |
| :--- | :--- | :--- | :--- |
| 판매자(자기 매장 주문) | `DELIVERED`·`PICKED_UP`·`REVIEWED` | 정산 `settledAt`부터 **7일 이내** | 정산이 `paid`가 **아님** (아니면 거부하고 "관리자에게 문의") |
| 관리자 | 같음 | 제한 없음 | 무관. `paid`면 회수 기록을 만든다 |

- 기간을 재는 기준 시각은 **정산 `settledAt` 하나로 통일**한다. 판매자 환불 기간과 정산 지급 지연(2.3)이 같은 시계를 쓰게 하기 위해서다. 정산 문서가 없으면(완료 처리 실패 등) 판매자 경로는 거부하고 관리자만 처리한다.
- 판매자 경로는 "기간 안"과 "정산이 `paid`가 아님"을 **같은 트랜잭션에서** 확인한다. 둘 중 하나라도 불확실하면 거부한다(fail closed).
- 대상은 파일럿에서 실제로 판매되는 **회차 주문**(`schemaVersion 2`)이다. 옛 일반 주문은 기존 관리자 경로를 그대로 둔다.

### 2.2 무엇을 하나 (전액 환불 한 번)

1. 사유 코드(`QUALITY_DAMAGED` 꽃 상함 · `BROKEN` 파손 · `WRONG_DELIVERY` 잘못 배송 · `OTHER` 기타)와 메모(필수, 길이 제한)를 받는다.
2. 기존 환불 서비스를 재사용해 **본 결제 전액**을 환불하고, 재배송비 결제가 있으면 기존 경로로 함께 환불한다.
3. 주문을 `CANCELLED`로 바꾸고 `cancellation`에 다음을 남긴다: 종류(배송 후 환불), 사유 코드, 메모, 누가(판매자/관리자 uid), 시각, 환불 금액.
4. 정산을 처리한다(2.3).
5. 손님에게 `ORDER_CANCELLED` 알림을 보낸다. `reason`에는 **사유 코드별 서버 고정 문구**를 넣는다(판매자 메모를 그대로 보내지 않는다).
6. 같은 요청을 두 번 보내도 환불은 한 번만 된다(기존 claim·멱등 방식 재사용).
7. **PortOne에서 이미 전액 취소된 결제**(임시 수동 절차로 콘솔 환불한 주문)면 추가 환불 호출 없이 로컬 기록만 맞춘다(관리자 경로).

### 2.3 정산

- **지급 가능 시점 = 배송 완료 7일 뒤**: `SETTLEMENT_CONFIRM_DELAY_DAYS=7`. 코드 기본값도 7로 맞춘다. 운영 값 변경은 별도 승인을 받는다.
- 정산이 `pending`·`confirmed`면 → `cancelled` (기존 동작).
- 정산이 `paid`면(관리자 경로에서만 발생) → 상태는 `paid`로 두고 **회수 기록**을 붙인다: 돌려받을 금액 = 그 정산의 판매자 지급액, 회수 상태 `PENDING`. 관리자가 "회수 완료"를 누르면 `RECOVERED`와 시각·처리자를 남긴다. 지금의 "경고 로그만"을 대체한다.
- 판매자·관리자 정산 집계에서 회수 대기 금액을 따로 보여 준다. 지급 합계를 소급해 바꾸지는 않는다.

### 2.4 화면

- 판매자 주문 상세: "배송 후 환불" 버튼과 확인 창(환불 금액 전액 표시, 사유 선택, 메모, "되돌릴 수 없음" 안내). 7일이 지났거나 정산이 지급됐으면 버튼 대신 "관리자에게 문의" 안내를 보여 준다. 기존 "소비자 반품 신청" 문구는 이 안내로 바꾼다.
- 관리자 주문: 같은 버튼(기간 제한 없음).
- 관리자 정산: "돌려받을 돈 ○○원" 표시와 "회수 완료" 버튼.

## 3. 파일럿 임시 수동 절차 (기능이 열리기 전, 또는 기능 장애 때)

기존 운영 절차서 `ops/mvp-sales-round-runbook.md` §8(수동 환불과 중복 방지)의 사전 조회·중복 방지 규칙을 그대로 따르고, 배송 뒤 환불은 아래를 덧붙인다.

1. 손님 연락(전화·카카오 채널)을 받으면 주문번호·사유·사진을 카카오 채널 대화로 확보한다.
2. 대표자가 환불 여부를 판단한다.
3. 결제 운영자가 PortOne 콘솔에서 **그 주문의 본 결제 한 건을 전액** 취소한다. 재배송비 결제가 있으면 별도 건으로 확인한다.
4. 손님에게 카카오 채널로 직접 "전액 환불 처리됐다"고 알린다(자동 알림은 가지 않는다).
5. **수동 환불 장부**(주문번호, 금액, 사유, 시각, 처리자)에 한 줄을 적는다. 고객 전화번호·주소는 적지 않는다.
6. **그 주문의 정산은 지급하지 않는다.** 이미 지급했다면 장부에 "돌려받을 돈"으로 적는다.
7. 기능이 열리면 장부의 주문마다 관리자 "배송 후 환불"을 한 번 눌러 기록을 맞춘다(2.2-7: 추가 환불 없이 기록만 맞춰짐). 맞춘 줄은 장부에 "기록 맞춤 완료"로 표시한다.
8. 주문을 Firestore에서 직접 `CANCELLED`로 고치지 않는다.

지급 지연 7일(2.3)이 운영에 반영되기 전까지는 **배송 완료 7일이 안 된 정산은 지급하지 않는 것**을 운영 규칙으로 둔다.

| **R5** | 관리자 배송 후 환불 API (기간 무제한, paid면 회수 기록, PortOne 이미 취소된 결제는 추가 호출 없이 로컬 수렴) + 회수 완료 API. **#576(어드민 행동 기록) 이후 코드 기준**: 기존 `forceRefund(orderId, dto, actorId)`·`markAsPaid(settlementId, actorId)`처럼 `actorId`를 받고, 성공 시 행동 기록을 남긴다(예: `admin.order.post_delivery_refunded`, `admin.settlement.recovery_completed`). 회수 완료는 `markAsPaid`의 `paidBy`처럼 처리자를 남긴다 | `apps/api/src/admin/admin.service.ts`·`admin.controller.ts`·`dto/admin.dto.ts`, 기록 화면 라벨 `apps/seller/src/app/admin/audit/_lib.ts` | 단위 테스트(10일차 성공·회수 PENDING, 원격 이미 취소 시 PortOne 취소 호출 0회, 회수 완료, 행동 기록 1건씩) | R3, R4(공통 환불 핵심 재사용), **#576 병합** |
| **R6** | 판매자 앱: 주문 상세 "배송 후 환불" 버튼·확인 창, 7일 뒤/지급 뒤 "관리자에게 문의", 반품 안내 문구 교체 | `apps/seller/src/app/orders/[id]/` | 타입·빌드, 로컬 육안(버튼 노출 조건 3가지) | R4 |
| **R7** | 관리자 화면: 주문 "배송 후 환불" 버튼, 정산 "돌려받을 돈" 표시·"회수 완료" 버튼 | `apps/seller/src/app/admin/` | 타입·빌드, 로컬 육안 | R5 |
| **R8** | 현행 계약 문서 갱신(배송 후 환불·회수 기록·지급 지연 7일) | `docs/specs/api/orders.md`·`settlements.md`·`payments.md`·`admin.md` | 문서가 R1~R7 구현과 일치 | R1, R3~R5 |
| **R9** | 로컬 E2E 시나리오: 배송 완료 → 판매자 환불 → 주문·결제·정산·알림 확인 / 8일차 판매자 거부 → 관리자 환불 | `apps/e2e/tests/` | `pnpm test:e2e:local` 통과, 테스트 데이터 정리 확인 | R4~R7 |

**동시에 진행할 수 있는 묶음:** R1 · R2는 서로 겹치지 않아 함께 진행할 수 있다(R0은 완료). 그 뒤 R3 → R4 → R5 순서로 직렬로 진행한다(같은 환불·정산 코드를 만지기 때문). R6과 R7은 각각 R4, R5가 끝나면 진행할 수 있다.

**출시 순서:** R0은 이번 주 안에 끝낸다. R1의 운영 값은 R4가 운영에 나가기 전에 적용한다. R4~R7은 한 번에 배포한다(release train). 배포 뒤 임시 장부의 주문을 R5 버튼으로 맞춘다.

## 5. 나중에 다듬을 것 (아이디어만)

- 손님 주문 화면에서 배송 후 환불된 주문을 "취소됨" 대신 "환불 완료"로 보여 주기
- 구매 화면 안내에 "꽃 상태 문제는 받은 날 카카오 채널로 사진과 함께 알려 주세요" 한 줄 추가(법무 확인 필요)
- 판매자 환불 확인 창에서 기사가 올린 배송 완료 사진을 함께 보여 주기(이미 있는 배송 사진 재사용)

## 6. 아직 열린 질문

1. **부분 환불**: 일부만 상했을 때 전액 대신 일부 보상이 필요해지면, 금액 입력 방식으로 다시 검토한다. 파일럿 동안 실제 요청 건수를 보고 정한다.
2. **거점에 도착했지만 손님이 찾아가지 않은 주문**(`HUB_ARRIVED`)이 시들었을 때의 환불은 이번 범위 밖이다. 지금은 관리자 판단 영역이다.
3. **새 "환불 완료" 알림 문구**(금액·입금 예정일 포함): 파일럿 뒤 필요하면 별도로 카카오 심사를 받는다.
