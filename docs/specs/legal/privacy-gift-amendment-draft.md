# 선물하기(`gift`) 개인정보처리방침 변경 초안

> 작성: 2026-10-18 KST
> 상태: **초안 — 미시행**. 운영 개인정보처리방침, `apps/consumer/src/app/privacy/page.tsx`, 정본
> `consumer-legal-documents.md`는 바꾸지 않았다. 이 문서는 법률 자문이 아니다.
> 기준 코드: `feat/benchmark-compare`(PR #547, main 미병합)

## 1. 왜 바꾸나

결제 화면에서 "선물로 보내요"를 켜면 지금 방침에 없는 정보가 새로 들어온다.

- 받는 분 이름
- 받는 분 휴대폰번호(= 배송 연락처)
- 보내는 분 이름
- 카드 문구(선택, 100자 이하)

받는 분은 회원이 아니고, 이 정보는 보내는 분(주문자)이 대신 적는다. 방침에 이 수집·이용·공유를 적고
시행한 뒤에만 운영에서 `gift` 기능 키를 켠다(4절).

## 2. 코드로 확인한 사실

| 무엇 | 사실 | 근거 |
|---|---|---|
| 입력 | 선물을 켜면 배송 연락처 칸이 "받는 분" 묶음으로 옮겨진다. 받는 분 휴대폰은 배송 연락처(`deliveryPhone`)와 같은 값이다 | `apps/consumer/src/components/benchmark/GiftFields.tsx` `giftPayload`, `apps/consumer/src/app/checkout/_components/CheckoutForm.tsx` |
| 형식 | 이름 2칸은 20자 한 줄, 휴대폰은 휴대폰 형식만, 카드 문구는 100자 한 줄로 정리. 이름·휴대폰이 없으면 주문을 막는다 | `apps/api/src/orders/_lib/round-order-extras.ts` `normalizeGift`, `packages/shared/src/benchmark.types.ts` `GiftInfo` |
| 저장 위치 | 회차 주문 문서(`orders/{id}`)의 `gift` 필드에 스냅샷으로 저장. 선물이 없으면 필드 자체가 없다 | `apps/api/src/orders/round-order-create.service.ts`, `round-order-extras.flow.spec.ts` |
| 브라우저 저장 | 결제 복귀용 `sessionStorage` 기록에는 선물 정보가 들어가지 않는다 | `apps/consumer/src/hooks/usePayment.ts`, `apps/consumer/src/lib/payment-redirect.ts` |
| 결제사 | PortOne 결제 요청에는 주문 이름·금액·결제수단만 보내고 선물 정보는 보내지 않는다 | `apps/consumer/src/hooks/usePayment.ts` `PortOne.requestPayment` |
| 주문자 화면 | 주문자 본인 주문 상세에 받는 분·연락처·보내는 분·카드 문구가 보인다 | `apps/consumer/src/app/mypage/orders/[id]/_detail.ts`, `OrderDetailExtras.tsx` |
| 판매자 | 자기 매장 주문 **상세**에서만 `gift` 전체(받는 분 이름·연락처, 보내는 분, 카드 문구)를 받는다. 목록에는 없다 | `apps/api/src/orders/seller-order-read-model.ts` `DETAIL_FIELDS`, `apps/seller/.../OrderBenchmarkSection.tsx` |
| 배송 기사 | `gift`를 받지 않는다. 기사에게 가는 이름은 주문자 계정 이름(`buyerName`)이고, 전화는 배정된 직배송 주문의 배송 중·보류 단계에서만 `deliveryPhone`(= 받는 분 휴대폰)이 간다 | `apps/api/src/orders/driver-order-read-model.ts` |
| 관리자 | 관리자 주문 조회는 주문 문서를 그대로 돌려주므로 `gift`가 포함된다 | `apps/api/src/admin/admin.service.ts` 주문 목록 |
| 거래성 알림 | 알림톡·SMS 수신번호는 주문 `deliveryPhone`을 먼저 쓴다. 따라서 선물 주문의 주문 알림 8종은 **받는 분 휴대폰으로 간다**. 접수 알림 본문의 `#{name}`은 주문자 이름이다 | `apps/api/src/notifications/notifications.service.ts` `resolveRecipientPhone`, `notification-templates.ts` |
| 보관·파기 | 자동 만료 삭제는 `legalOrderRecords` 등 보관 기록 컬렉션만 대상이고, 이 기록에는 주문 식별자·금액·상태만 있고 선물 정보는 없다(5년 뒤 삭제). 선물 정보가 든 **주문 문서는 자동 삭제되지 않는다** — 현재 방침의 "일반 주문 정보 자동 만료 삭제 미구현, 운영자 파기"와 같은 처지다 | `apps/api/src/retention/retention.service.ts` `RETENTION_POLICIES`·`purgeExpiredRecords` |
| 취소 | 주문이 취소돼도 `gift` 필드를 지우는 코드는 없다 | `apps/api/src` 전체 `gift` 검색 결과 |
| 기능 키 | `gift` 키는 화면(소비자·판매자 앱 빌드 값 `NEXT_PUBLIC_GREENHUB_FEATURES`)에서만 켜고 끈다. API는 키와 상관없이 요청에 `gift`가 있으면 받아 저장한다 | `packages/shared/src/features.ts`, `apps/consumer/src/lib/features.ts`, API에 기능 키 확인 없음 |

### 확인하지 못한 것(확인 필요)

- 운영 Firestore 백업의 보관 기간과, 백업 안의 주문 문서 파기 방법.
- 카드 문구를 실제로 어떻게 전달하는지(판매자가 손글씨 카드로 옮기는지, 인쇄하는지) — 코드에는 판매자 화면 표시까지만 있다.
- 받는 분이 주문 알림을 받는 것이 의도된 동작인지 — 코드상 결과일 뿐 결정 기록은 찾지 못했다.

## 4. `gift` 기능 키를 켜는 조건

1. 이 초안이 결정(6절)을 반영해 정본 `consumer-legal-documents.md`와 `/privacy` 화면에 들어가고, 그 판이
   운영에 배포된다.
2. 고지 기간(공지일 + 7일 이상)이 지나 시행일이 된다.
3. 그 뒤에 운영 빌드 값 `NEXT_PUBLIC_GREENHUB_FEATURES`에 `gift`를 넣는다(소비자·판매자 앱 함께).

시행 전에는 운영에서 `gift`를 켜지 않는다. API는 키와 무관하게 `gift`를 받으므로, 시행 전에 서버에서도
막을지는 결정 D7로 남긴다.

## 5. 시행일과 고지 방법(제안)

- **시행일**: 공지일로부터 7일 뒤 이상. 정확한 날짜는 사용자가 정한다(D1).
- 2026-11-01 개정판이 아직 운영에 나가지 않았다면, 두 개정을 한 판으로 합쳐 한 번만 고지하는 방법도
  있다. 이때 시행일은 합친 판의 배포일 + 7일 이상으로 다시 정한다.
- **고지 방법 제안**
  - `/privacy` 화면 상단 또는 10절에 "변경 예정 안내(시행일·바뀌는 내용·이유)"를 시행 전에 게시
  - 소비자 앱 공지(홈 배너 또는 공지 영역)에 시행일과 요약 한 줄
  - 이전 판 보관: 현재 판 문구를 볼 수 있는 경로 유지(기존 10절 원칙)
  - 회원 대상 개별 알림(알림톡·이메일)은 필수 여부를 사용자가 판단(현재 파일럿은 마케팅 발송을 하지
    않으므로 거래성 채널로 보낼지 따로 결정)
